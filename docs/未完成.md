## 二、状态效果系统（模块 A）—— ❌ 未实现

**现状：** 无 `StatusEffectManager`、无 `statusEffects.json`。

### A.1 数据结构

```typescript
interface StatusEffect {
  id: string;               // "poison", "rage", "shield", "freeze"
  name: string;
  type: 'buff' | 'debuff';
  duration: number;         // 持续回合数，-1 表示永久
  stackable: boolean;
  maxStacks?: number;
  icon?: string;
  description: string;
  onTurnStart?: (target: Combatant, instance: StatusEffectInstance) => void;
  onTurnEnd?: (target: Combatant, instance: StatusEffectInstance) => void;
  onDamageDealt?: (damage: number, source: Combatant, target: Combatant, instance: StatusEffectInstance) => number;
  onDamageReceived?: (damage: number, target: Combatant, source: Combatant, instance: StatusEffectInstance) => number;
  onApply?: (target: Combatant, instance: StatusEffectInstance) => void;
  onRemove?: (target: Combatant, instance: StatusEffectInstance) => void;
}

interface StatusEffectInstance {
  effectId: string;
  stacks: number;
  remainingTurns: number;
}
```

### A.2 核心逻辑（StatusEffectManager 单例）

- `applyStatus(target, effectId, stacks?, duration?)`：同类可叠则增 `stacks` 并刷新时长；否则新增实例并调用 `onApply`。
- `removeStatus(target, effectId)`：移除并调用 `onRemove`。
- `processTurnStart(target)`：遍历调用 `onTurnStart`，时长递减，归零移除。
- `processTurnEnd(target)`：遍历调用 `onTurnEnd`。
- `getActiveEffects(target)`：返回当前所有激活效果。

### A.3 预置效果清单

| effectId | 名称 | 类型 | 持续 | 效果 |
| :--- | :--- | :--- | :--- | :--- |
| `poison` | 中毒 | debuff | 3 回合 | 每回合损失最大生命 5%，可叠 3 层 |
| `rage` | 狂暴 | buff | 3 回合 | 攻击+30%，防御−20% |
| `shield` | 护盾 | buff | 永久至击破 | 吸收下一次伤害 = 防御×2 |
| `freeze` | 冰冻 | debuff | 1 回合 | 目标下回合无法行动 |
| `burn` | 灼烧 | debuff | 2 回合 | 每回合 10+攻击者等级×2 固定伤害，可叠 5 层 |
| `haste` | 急速 | buff | 5 回合 | 闪避+15% |
| `bless` | 祝福 | buff | 3 回合 | 伤害加成+10% |
| `curse` | 诅咒 | debuff | 3 回合 | 攻击−15%，不可叠加 |

# 三、数值平衡设计（层级难度 · 待实现）

> **状态：** 🚧 设计中（待实现）｜**创建：** 2026-09-10
> **目的：** 为「饰品（第 3 槽）+ 遗物（待加入）」带来的玩家增益预留敌人强度空间，并强化**层级之间的难度落差**。
> **关联代码：** `src/data/tiers.ts`（区段单一数据源）、`src/utils/StatCalculator.ts`、`src/data/gameConfig.json`、`src/data/monsters.json`
> **关联文档：** `docs/遗物系统设计.md`（玩家增益来源）

---

## 0. 术语约定（重要）

| 术语 | 含义 | 示例 |
| :--- | :--- | :--- |
| **层级** | 按美术风格划分的**大区段** | 1–15、16–40、41–60、61–80、81–100、101–110 |
| **楼层** | **单个**楼层 | 第 1 层、第 2 层、第 41 层 |

> 全文严格遵循：谈"层间落差"用**层级**；谈"逐层递增"用**楼层**。

---

## 1. 现状诊断（代码实测）

**怪物属性公式：**

```
怪物属性 = floorAnchors 插值(1–50 楼层) × 怪物倍率(hpMul/atkMul/defMul) × 深度倍率 × 精英/Boss 加成
```

- 锚点仅定义到 **50 楼层**（`gameConfig.floorAnchors`），51 楼层以上按 `overflowPerFloor` 递增（hp +8%/楼层，atk/def +5%/楼层）。
- 精英 ×1.25；Boss 靠 `hpMul 5.0`（`bossStatBonus` 全为 0）；全塔仅 1 种 Boss。
- **核心问题：层级边界无阶跃。** 锚点为连续插值，跨越层级（第 16 / 41 / 61 / 81 / 101 楼层）时敌人强度几乎不变：

| 边界 | 上一层级末 hp | 下一层级初 hp | 跳变 |
| :--- | :--- | :--- | :--- |
| 15→16 楼层 | ≈685 | ≈728 | 仅 +6% |

→ 与六套美术主题的"层级切换"脱节，玩家感受不到跨层级的压迫感。

---

## 2. 设计意图（用户确认）

1. **前两层给面子**：不依靠运气（遗物）也能**较轻松**推到**层级 2 中期**（约 28–32 楼层）。
2. **层级 3 是分水岭**：没有较大提升（好遗物 / 饰品 / 高品质装备）就**步步维艰**。
3. **前期数值基本不动**：前期拿不到好遗物，不额外加压。
4. 「**运气也是实力的一部分**」：后期允许"运气差就卡"，但需有资源保底，避免完全无解。

---

## 3. 方案：层级阶跃倍率 `tierScale`（v2 · 前平后陡）

在现有公式上**再乘一个层级系数**，使每个层级边界产生明显跳变：

| 层级 | 楼层区间 | `tierScale`（草案） | 边界跳变（含锚点） | 设计意图 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 1–15 | ×1.00 | — | 完全不变，前期轻松 |
| 2 | 16–40 | ×1.05 | 15→16 约 **+11%** | 几乎无感，轻松推到中期 |
| 3 | 41–60 | ×1.45 | 40→41 约 **+46%** | ⚠️ **分水岭**：无提升即卡 |
| 4 | 61–80 | ×2.00 | 60→61 约 **+49%** | 需要成型的遗物 / 饰品 |
| 5 | 81–100 | ×2.70 | 80→81 约 **+46%** | 运气与 build 的双重考验 |
| 6 | 101–110 | ×3.50 | 100→101 约 **+40%** | 终局，拼最终 build |

**实现落点（最小改动）：**

- **数据**：`src/data/tiers.ts` 新增 `statScale`（可选 `goldScale` / `expScale`），保持"区段单一数据源"，勿在他处另抄。
- **逻辑**：`StatCalculator.monsterStats()` 乘 `tierScale(floorId)`，与 `depthMul` 并列。
- **配套**：`overflowPerFloor` 改为**分层级**（后期层级的 hp/atk 递增率差异化）。

---

## 4. 玩家侧增益估算（为"增强多少"提供依据）

| 来源 | 增益量级 |
| :--- | :--- |
| 饰品（第 3 槽，顶级） | 暴击 / 闪避 **+14~24%** |
| 遗物（预估 3~5 件通用） | 攻击 +30~60%、生命 +30~100% + 机制类（吸血 / 复活 / 金币） |
| **合计有效战力** | **后期 +60%~150%** |

→ 敌人整体需 **+40%~80%** 才匹配，故后段层级更陡。

---

## 5. 配套（否则"步步维艰"会变成"死路"）

1. **资源供给随难度上调**：层级 3 起，宝箱 / Boss 掉落池、商人库存同步上调（遗物概率本就随楼层与难度递增）。
2. **后期曲线重标定**：现锚点外推第 81 楼层普通怪 hp ≈ 11 万，再 ×2.7 会逼近 `maxTurns=60`；建议**下调 51+ 楼层 overflow**（如 hp 8%→6%）给 `tierScale` 让位，避免"乘两次"爆表。
3. **难度系统叠加顺序**：难度 7 档落地时，`最终倍率 = 难度系数 × tierScale`，需明确谁是主、谁是修饰。

---

## 6. 验证方案

新增 `src/test/balanceTest.ts`（无头）：对每层级抽样"典型 build（无遗物 / 1 件 / 3 件）"，输出**回合数 / 损耗 / 存活率**。验收标准：

- 层级 1–2：无遗物 build 损耗 **< 15%**（轻松）
- 层级 3：无遗物 build **明显卡顿**（损耗 > 60% 或频繁撤退）
- 层级 4–6：需 **≥1~3 件有效遗物**才顺畅

---

## 7. 待定项

1. `tierScale` 最终数值（本表为草案，需 `balanceTest` 校准）。
2. 是否采用"层内线性过渡"（如层级 2 内从 1.00 缓升到 1.10）替代整段常数。
3. `overflowPerFloor` 分层级的具体数值。
4. `depthMultiplier`（现按 1–10 / 11–30 / 31+ 三档）对齐到六层级。
5. 与难度系统（7 档）的叠加规则。
6. 金币 / 经验的层级缩放是否同步（`goldScale` / `expScale`）。

## 一、种子格式

种子为 **10 位数字**，结构如下：

```
[版本:1位][难度:1位][初始运气:2位][地图数值:4位][预留:2位]
```

| 段位 | 位数 | 取值范围 | 用途 |
| :--- | :--- | :--- | :--- |
| 版本 | 1位 | 0-9 | 0=当前版本 |
| 难度 | 1位 | 1-7 | 1摇篮曲~7天堂 |
| 初始运气 | 2位 | 01-07 | 01=-3 ~ 07=+3 |
| 地图数值 | 4位 | 0000-9999 | 地图生成的随机源 |
| 预留 | 2位 | 00-99 | 未来扩展 |

**示例：** `001040000` = 版本0 + 摇篮曲 + 中性运气 + 地图0000 + 预留00

## 二、解析规则

```typescript
parseSeed("001040000"):
  version = 0
  difficulty = 1 → 摇篮曲
  initialTension = 04 - 4 = 0（中性）
  mapSeed = 0000
  reserved = 00
```

- 不足 10 位左补零，超出取后 10 位
- 非数字输入自动转哈希
